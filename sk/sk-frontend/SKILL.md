# 프런트엔드 구현

요구사항·티켓·API 계약과 현재 프로젝트 지침을 확인한다. React 또는 Next.js와 TypeScript를 기본으로 하고 이미 확정된 기술 선택을 유지한다.

## 구조

새 화면과 컴포넌트를 배치하기 전에 [웹 구조](references/web-structure.md)를 읽는다. 핵심 방향은 `route → screen → component → ui`다. `ui`는 화면·기능 계층을 참조하지 않는다. 기존 앱은 요청 범위의 파일부터 적용하고 대규모 이동을 섞지 않는다.

## 구현

1. 티켓의 사용자 행동과 화면 상태를 확인한다. 핵심 흐름을 실제 API와 연결해 끝까지 동작시키는 단위를 선택한다.
2. API 타입, 요청·응답·오류 형식, 인증 전달 방식이 맞는지 확인한다. 프런트에서 서버의 비즈니스 규칙을 유일한 검증 수단으로 구현하지 않는다.
3. 상태는 필요한 가장 가까운 소유자에 둔다. 서버 데이터·입력 상태·파생 값을 구분하고 계산 가능한 값을 별도 상태와 Effect로 동기화하지 않는다.
4. 필요한 로딩·빈 결과·오류·완료 상태, 중복 제출 방지, 재시도와 입력 보존을 구현한다.
5. 폼 라벨, 키보드 조작, 포커스, 작은 화면을 확인한다. 사용하지 않는 라이브러리나 과도한 추상화를 추가하지 않는다.

Next.js에서는 서버·클라이언트 경계를 기능에 맞게 정하고 브라우저에 비밀 값을 보내지 않는다. NestJS와의 책임을 중복하지 않는다. 캐시·메모이제이션은 일관성과 실제 비용을 확인해 적용한다.

## 확인과 보고

관련 타입·린트·빌드 검사와 변경한 사용자 흐름을 확인한다. 실제 API 연결과 mock 동작을 구분한다. 결과에는 요구사항·티켓 연결, 주요 변경, 실행한 검증, 남은 제한 사항을 남긴다. 결함 수정은 해당 티켓의 반복 예산 안에서 수행한다.

검색 도구를 통한 웹 검색·문서 조회는 허용한다. 브라우저 화면 조작·Computer Use·브라우저 자동화 E2E는 사용하지 않는다. UI는 사용자가 직접 확인할 단계와 예상 결과를 안내하고, 아직 확인받지 않은 항목은 미검증으로 남긴다.

## 실행 비용

확정 UI의 반복 구현은 경량 또는 일반 역할에, 상태 경합·인증 경계·복잡한 렌더링 문제는 심층 역할에 맞춘다. 폴더·파일 검사는 도구로 처리하고 전체 저장소를 매번 읽지 않는다.
