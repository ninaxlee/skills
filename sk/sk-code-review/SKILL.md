# 근거 중심 코드 리뷰

실제 동작 경로와 요구사항을 읽고 지적한다. 설계 선택의 비교와 실행 검증은 각각 다른 작업이며 리뷰가 이를 대신하지 않는다.

## 범위 정하기

사용자가 지정한 파일·미커밋 변경·커밋 구간을 사용한다. 지정이 없으면 현재 변경분을 우선 확인하고 범위를 알린다. `git diff`뿐 아니라 새 파일과 호출자·스키마·계약을 필요한 만큼 추적한다. 고정 비교점이 필요하나 알 수 없을 때만 질문한다.

## 검토 축

1. 요구사항: 누락, 잘못 구현한 규칙, 요청 범위 밖 동작과 정상·실패 경로.
2. 로직: 불필요한 분기·반복·변환, 죽은 코드, 중복 규칙, 이름으로 숨겨진 책임, 근거 없는 범용화.
3. 데이터: N+1, 중복 조회, 과다 조회, 집계 위치, 페이지네이션, 인덱스, 트랜잭션·경쟁 상태.
4. 비동기·프런트: 독립 작업의 직렬 실행, 중복 요청, 취소·응답 순서, 중복 상태·Effect, 불필요한 렌더링.
5. 경계: 인증·권한·입력 검증, 정보 노출, 프런트·서버 계약 불일치와 오류 누락.
6. 유지보수: 실제 변경 비용을 키우는 결합, 책임 역전, 웹의 ui/component/screen 역방향 의존.

린터가 해결할 포맷 지적을 반복하지 않는다. 함수가 길거나 코드가 중복됐다는 이유만으로 추상화를 강제하지 않는다. 비슷한 코드가 서로 다른 이유로 변하는지 확인한다.

## 지적 형식

각 발견에 심각도, 파일·위치, 발생 조건, 근거, 영향, 최소 수정안, 검증 방법을 붙인다.

- P1: 핵심 기능 불능, 데이터 손상·노출 등 우선 수정할 결함.
- P2: 특정 조건에서 발생하는 오동작이나 의미 있는 성능·복잡성 문제.
- P3: 근거가 있는 작은 개선. 선택적 제안으로 표시한다.

확정 결함과 추가 확인이 필요한 가설을 구분한다. “최적화 가능”만으로 지적하지 않는다. 성능 수치나 실행 계획을 보지 못했으면 측정했다고 쓰지 않는다. 유효한 문제가 없으면 없다고 보고한다.

쿼리는 요청당 횟수 외에 조회량·실행 계획·연결·메모리·정합성을 함께 본다. 독립 호출을 모두 동시 실행하거나 캐시를 추가하는 것이 항상 개선이라고 가정하지 않는다.

## 결과와 실행 비용

중요한 발견부터 보고하고 검토 범위·실행한 확인·남은 불확실성을 덧붙인다. 리뷰만 요청했으면 코드를 수정하지 않는다. 수정까지 요청되면 동작을 보존하는 최소 변경과 관련 검증을 수행한다.

파일 탐색·참조 수집은 경량 역할로 묶을 수 있다. 실제 결함 판단, 쿼리 비용·권한·정합성 검토에는 일반 또는 심층 역할을 사용한다. 매 리뷰마다 여러 에이전트를 자동 생성하지 않는다.
