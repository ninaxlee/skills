# NestJS 백엔드 구현

요구사항·티켓·API 계약과 기존 모듈을 확인한다. NestJS와 TypeScript를 기본으로 한다. DB·ORM·인증 제공자·배포 환경은 합의된 선택을 따른다.

## 책임과 계약

- 도메인·기능 단위 모듈에 controller, service와 필요한 데이터 접근 코드를 둔다.
- controller는 HTTP 입력과 응답 경계를, service는 유스케이스와 비즈니스 규칙을 담당한다. 단순 CRUD에 계층을 기계적으로 추가하지 않는다.
- 요청·응답·상태 코드·오류 형식·권한·페이지네이션을 프런트 계약과 맞춘다. 공개 응답에 내부 필드나 비밀을 노출하지 않는다.
- DTO와 실행 시 검증으로 신뢰 경계를 지킨다. TypeScript 타입만으로 외부 입력이 검증됐다고 보지 않는다.
- 인증과 리소스별 권한을 구분한다. 로그인 여부만 확인하고 다른 사용자의 데이터를 허용하지 않는지 검토한다.

## 데이터와 비동기

- 실제 사용 경로의 조회 수·조회량을 파악한다. 반복문 속 DB 호출, 중복 조회, 불필요한 컬럼·전체 목록 로드를 피한다.
- JOIN·일괄 조회·동시 실행은 결과 크기, 연결 수, 순서와 정합성까지 비교한다. 쿼리 수만 줄이고 총비용을 키우지 않는다.
- 트랜잭션, 유일 제약, 동시 수정 정책은 요구되는 불변식에 맞춘다. 외부 호출을 트랜잭션 안에 넣는 비용도 고려한다.
- 중복 제출·부분 실패·재시도에 필요한 정책을 확인한다. 모든 API에 같은 재시도 정책을 적용하지 않는다.
- 캐시와 인덱스는 실제 읽기·쓰기 패턴과 무효화 비용을 확인해 적용한다.

## 확인과 보고

실제 API 요청으로 정상·실패·권한 경로를 확인하고 데이터 변화가 요구사항과 일치하는지 검증한다. 중요한 규칙과 회귀 위험에는 적절한 자동 검사를 추가한다. DB 연결이 없거나 mock만 확인했다면 명시한다.

변경한 API 계약과 실행·환경변수 변경을 문서에 반영한다. 미확정 데이터 정책을 임의로 확정하지 않는다. 수정·재검증은 티켓 예산에 따른다.

## 실행 비용

정해진 DTO·단순 엔드포인트의 반복 구현은 경량 또는 일반 역할에 맞는다. 권한, 동시성, 트랜잭션, 마이그레이션과 성능 원인 분석은 심층 역할에서 검토한다.
