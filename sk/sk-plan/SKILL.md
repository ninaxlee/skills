# 실행 계획과 티켓

요구사항, 결정 기록, 현재 코드와 가용 시간을 확인하고 구현·검증까지 끝낼 수 있는 단위로 작업을 나눈다.

## 작업 나누기

- 초기 실행 환경과 프런트·서버 연결이 필요한지 먼저 확인한다.
- 사용자에게 보이는 기능을 수직으로 자른다. 예를 들어 “신청 등록”은 화면, API, 저장, 실패 처리, 완료 확인을 함께 다룬다.
- 한 티켓이 너무 크면 독립적으로 검증할 수 있는 흐름으로 나눈다. 프런트 전체·백엔드 전체만으로 분리해 통합을 뒤로 미루지 않는다.
- API 요청·응답·오류 계약과 선행 결정이 필요한 작업을 먼저 드러낸다.
- 완료 조건에 필수 사용자 동작과 검증 방법을 포함한다. 구현 파일을 만들었다는 사실만으로 완료 처리하지 않는다.

## 티켓 정보

기존 관리 방식이 있으면 따른다. 없으면 `docs/tasks.md`에 아래 정도로 기록한다.

```markdown
### T-001 신청 등록
- 요구사항: R-001
- 상태: ready
- 목적과 범위: 사용자가 유효한 신청을 등록하고 결과를 확인한다.
- 의존성: 입력 정책과 API 계약 확정
- 완료 조건: 정상 등록, 유효하지 않은 입력 거절, 중복 제출 정책 확인
- 검증: 해당 API 검사와 브라우저 등록 시나리오
```

상태는 `ready`, `in-progress`, `blocked`, `done`을 기본으로 하되 기존 규칙을 우선한다. 막힌 이유와 필요한 결정, 검증 증거를 연결한다. 대화에서 계획을 요청한 것만으로 외부 이슈를 생성하지 않는다.

## 진행과 재계획

- 필수 기능의 가장 작은 동작 경로를 먼저 완성하고 점진적으로 확장한다.
- 실패나 요구 변경으로 범위가 달라지면 관련 티켓·의존성·완료 조건만 갱신한다.
- 재시도와 수정은 해당 티켓의 예산 안에서 수행한다. 검증이 실패한 티켓을 완료로 바꾸지 않는다.
- 잔여 시간을 고려해 확장 후보를 미룰 수 있지만 필수 조건은 사용자 결정 없이 삭제하지 않는다.

## 실행 비용

확정 명세의 티켓 변환은 경량 역할로 묶어 처리한다. 의존성 충돌, 범위 조정, 불확실한 작업의 분할은 일반 또는 심층 역할이 판단한다.
