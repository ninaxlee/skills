# 요구사항 명세

원문에서 확인한 사실과 해석, 가정, 사용자가 결정할 항목을 구분한다. 기존 프로젝트의 지침과 명세가 있으면 먼저 확인한다.

## 진행

1. 대상 사용자, 해결할 문제, 핵심 행동, 입력과 출력, 운영 제약을 추출한다. 원문 위치나 문장을 근거로 연결한다.
2. 요구사항에 `R-001` 같은 안정적인 ID를 부여한다. 기존 ID를 유지하고 변경·제외 이력을 남긴다.
3. 각 요구사항에 우선순위, 정상·실패 인수 조건, 의존성, 미확정 사항을 붙인다. 성능·보안·접근성 조건은 제공된 제약과 실제 기능에 맞춰 정한다.
4. 필수 범위와 이후 확장 후보를 구분한다. 원문에 없는 기능을 필수로 승격하지 않는다.
5. 구현을 막는 질문과 가정을 표시한다. 질문이 필요하면 환경에서 확인 가능한 사실을 먼저 조사하고, 선택과 의도만 사용자에게 묻는다.

예: “신청할 수 있다”는 요구에는 허용되는 입력, 중복 제출 시 동작, 성공 확인 방법이 필요하다. 알려지지 않은 정책을 임의로 확정하지 않는다.

## 결과

기존 문서가 있으면 갱신한다. 새 문서가 필요하면 `docs/requirements.md`에 다음을 간결하게 남긴다.

- 문제와 핵심 사용자 흐름.
- ID별 요구사항, 우선순위, 인수 조건, 원문 근거.
- 확정 범위, 제외 범위, 가정과 결정 대기 항목.

인수 조건은 관찰할 수 있는 결과로 쓴다. “빠르게”, “직관적으로”, “잘 처리한다”는 표현에는 확인 기준이 필요하다. 검증되지 않은 가정을 확정 요구사항처럼 기록하지 않는다.

## 실행 비용

단순 추출·분류는 경량 역할에 묶어 맡길 수 있다. 상충하는 요구, 범위 변경, 정합성에 영향을 주는 해석은 심층 역할에서 검토한다. 위임은 프로젝트 모델 정책과 사용 가능한 도구 범위 안에서 수행하며, 짧은 분석은 현재 에이전트에서 끝낸다.
