# 주요 결정 검토

현재 요구사항과 제약을 기준으로 결정의 근거와 실패 조건을 검토한다. React 또는 Next.js와 NestJS를 기본 후보로 두며 DB, ORM, 배포 제공자는 고정하지 않는다.

## 비교

1. 결정할 질문, 현재 제안, 이미 확정한 제약을 적는다.
2. 실현 가능한 대안을 고른다. 현재 방식 유지와 가장 단순한 구현도 후보가 될 수 있다.
3. 사용자 가치, 구현 시간, 운영 부담, 데이터 정합성, 변경 비용 가운데 관련 기준으로 비교한다.
4. 각 대안의 실패 시나리오와 숨은 전제를 찾는다. 실제 요구가 없는 확장성을 위해 복잡성을 추가하는지 확인한다.
5. 권고안과 그 권고가 바뀌는 조건을 제시한다. 수치를 알 수 없으면 측정·실험으로 확인할 항목을 제안한다.

Next.js와 NestJS를 함께 쓰면 인증, 데이터 접근, 비즈니스 로직의 책임 경계를 확인한다. 서버 로직을 양쪽에 중복 구현하는 선택에는 명시적인 이유가 필요하다.

## 사용자 결정

제품 범위, 프레임워크, 저장 방식, 인증 정책, 외부 서비스 의존처럼 영향이 큰 선택은 사용자가 비교하고 결정한다. 사용자가 이미 선택했거나 위임한 범위는 반복 승인받지 않는다. 결정과 무관한 조사·초안은 계속 진행한다.

결정 기록이 필요하면 `docs/decisions.md`의 `D-001` 항목 등에 다음을 남긴다.

- 결정 질문과 요구사항 연결.
- 후보별 이점·비용·실패 조건.
- 권고와 사용자 선택, 선택 근거, 재검토 조건.

반대를 위한 반대나 모든 대안의 점수화를 강요하지 않는다. 근거가 충분하면 현재 선택을 유지한다. 코드의 실제 결함은 위치와 재현 조건이 있는 코드 리뷰로 넘긴다.

## 실행 비용

사실 수집은 경량 역할로 제한하고, 대안의 타당성·정합성 판단은 일반 또는 심층 역할에서 수행한다. 비용이 큰 실험은 결정에 필요한 가장 작은 범위로 제안한다.
