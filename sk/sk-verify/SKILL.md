# 실행 검증과 제한된 개선 루프

완료 조건을 실제 동작과 대조한다. 수정 권한이 포함된 요청이면 아래 루프로 진행하고, 검증·리뷰만 요청했으면 재현과 결과 보고까지 수행한다.

## 검증 설계

1. 요구사항·티켓·현재 변경을 확인해 이번 실행의 완료 조건을 고정한다.
2. 각 조건에 적절한 증거를 연결한다. 타입 검사·린트·빌드, API·저장 결과, 브라우저 사용자 흐름은 서로 다른 사실을 검증한다.
3. 가장 작은 실패 검사를 먼저 실행하고 필요한 통합 경로로 넓힌다. 핵심 흐름의 정상·오류·권한·중복 제출 중 관련 경로를 선택한다.
4. 실제 API·데이터 연결과 mock을 구분한다. 도구·환경이 없으면 확인 못한 항목과 이유를 남긴다.

검색 도구를 통한 웹 검색·문서 조회는 허용한다. 브라우저 화면 조작·Computer Use·Playwright·Selenium 등 브라우저 자동화 E2E는 사용하지 않는다. 터미널·API 검사와 사용자 수동 확인을 나눠 진행하고, 사용자가 확인하지 않은 UI 항목은 `미검증`으로 남긴다.

## 반복 정책

반복 전에 [루프 정책](references/verification-loop.md)을 읽는다. 프로젝트·사용자 예산이 있으면 우선하고, 없으면 한 티켓에 **수정 사이클 최대 3회, 경과 시간 15분 중 먼저 도달하는 한도**를 사용한다. 초기 검사도 시간 예산에 포함한다. 장시간 검사는 시작 전에 남은 시간을 확인한다.

- 검사 → 실패 재현 → 원인 가설 → 최소 수정 → 관련 재검증 순으로 진행한다.
- 동일 실패가 연속 2회이고 새 근거가 없으면 현재 접근을 멈추고 가설·도구·역할을 바꾼다. 전략 변경도 같은 예산에 포함한다.
- 완료 조건을 충족하면 즉시 종료한다. 이미 통과한 검사는 관련 코드·계약·환경이 바뀌거나 회귀 우려가 생긴 경우에만 반복한다.
- 예산이 끝나거나 필요한 사용자 결정·외부 조건 때문에 진행할 수 없으면 루프를 종료하고 현재 상태와 다음 행동을 보고한다.
- 재귀 위임, 모델 변경, 티켓 분할, 새 대화로 같은 문제의 예산을 초기화하지 않는다. 실패 횟수를 감추거나 완료 조건을 낮춰 성공으로 만들지 않는다.

## 증거와 보고

각 인수 조건에 `통과`, `실패`, `미검증`을 표시한다. 명령과 종료 결과, API 응답·데이터 상태, 브라우저 재현 절차 등 실제 관찰을 붙인다. 검증한 변경 상태도 식별한다.

루프를 사용했다면 실패 원인, 변경, 재검증, 사이클 수와 종료 이유를 남긴다. 기록은 티켓 또는 `docs/verification.md`에 필요한 만큼 유지하고 원시 로그를 문서에 전부 복사하지 않는다.

## 실행 비용

명령 실행과 명확한 결과 판독은 도구·경량 역할로 처리한다. 원인 불명 실패, 권한·정합성 문제는 심층 역할에 필요한 증거만 전달한다. 상향 전 새로운 분석이 필요한지 판단하고 무조건 같은 검사를 반복하지 않는다.
