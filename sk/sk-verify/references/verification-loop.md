# 반복 검증 운영

## 범위와 예산

한 루프는 한 티켓 또는 명시한 완료 조건 묶음에 대응한다. 수정 사이클은 원인 가설에 따른 코드·설정 변경과 그 뒤의 관련 재검증을 뜻한다. 단순 상태 조회나 명령을 나눠 실행한 것은 별도 사이클이 아니다.

기본 한도는 수정 사이클 3회, 경과 시간 15분 중 먼저 도달하는 조건이다. 프로젝트에 더 구체적인 예산이 있으면 따른다. 여러 티켓을 수행하는 요청이면 처음에 전체 시간·사용량 예산도 정하고 공유한다. 티켓 분할로 예산을 늘리지 않는다.

실제 토큰 사용량을 얻을 수 있을 때만 토큰 한도를 적용하고 측정한다. 사용할 수 없으면 호출·위임 수, 사이클, 시간으로 제어하며 절약 토큰 수를 추정해 사실처럼 쓰지 않는다. 사용량 수집 기능이 없는 런타임에서 정밀한 토큰 제한을 보장하지 않는다.

## 상태 전이

```text
완료 조건·예산 설정 → 검사
  통과 → 증거 확인 → 완료
  실패 → 재현·분류
    구현 결함 → 가설 → 최소 수정 → 관련 재검증
    환경·외부 조건 → 설정 확인 → 가능한 독립 검증 → 한계 보고
    요구·정책 불명 → 필요한 결정 제시 → 의존 작업 보류
```

환경 실패를 기능 결함으로 오인해 코드를 반복 수정하지 않는다. 외부 연결 불가·누락 자격증명·포트 충돌·실행 도구 부재를 먼저 분류한다. 실제 서비스에 영향을 주는 재시도는 현재 권한과 중복 처리 정책 안에서만 한다.

## 다음 시도를 할 근거

다음 중 하나가 있어야 다시 시도한다.

- 실패 지점과 입력을 더 좁혔다.
- 새로운 로그·응답·스택·실행 계획을 얻었다.
- 근거 있는 가설을 수정했고 그 효과를 검사할 수 있다.
- 알려진 일시 실패이며 재시도의 부작용과 한도가 정해져 있다.

같은 실패가 두 번 연속이고 근거가 늘지 않으면 전략을 바꾼다. 더 높은 effort는 새로운 분석이 필요한 경우에만 사용한다. 도구 오류나 정보 부족은 모델만 높여 해결된다고 가정하지 않는다.

## 검증 선택

- 수정한 부분의 실패 검사를 먼저 재실행한다.
- 계약·공유 상태·공통 컴포넌트를 바꿨으면 영향을 받는 경로로 넓힌다.
- 관련 검증이 통과하면 원래 완료 조건의 충족 여부를 확인한다.
- 최종 코드 상태가 검증 당시와 달라졌으면 영향받은 검증 결과를 낡은 것으로 표시하고 필요한 것만 다시 실행한다.

종료 보고에는 통과·실패·미검증, 마지막 관찰, 시도한 변경, 남은 원인 가설, 사용한 예산, 재개에 필요한 조건을 남긴다. 예산 종료는 성공을 뜻하지 않는다.
